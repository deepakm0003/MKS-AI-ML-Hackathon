# Milestone 4 — Dashboard: architecture, design system and Phase 1 audit

## 1. Audit (before Phase 1)

| Area | Finding | Decision |
|---|---|---|
| Frontend | `dashboard/` was an empty placeholder; no frontend code, routes or styles existed. `requirements.txt` listed Streamlit + Plotly but nothing used them. | New React + TypeScript app in `dashboard/`. Streamlit cannot deliver the brief (enterprise shell, shared URL filters, custom design system, sub-second interactions). |

| Tooling | Node 22.14, npm 11.6; registry reachable. | Vite 5 + React 18 + React Router 6 + Vitest; **3 runtime dependencies**, no UI kit, no CSS framework, no icon library. Chart library chosen in Phase 2 (see §6). |

## 2. Design research — what makes a planning dashboard read as "enterprise"

* **Hierarchy and reading order.** Headline KPIs top-left, then trends, then breakdowns, then
  detail tables; the most important question answered first
  ([FusionCharts](https://www.fusioncharts.com/blog/dashboard-design-best-practices/),
  [O'Reilly / Power BI](https://www.oreilly.com/library/view/mastering-microsoft-power/9781788297233/29740924-7375-4580-9963-39235408b627.xhtml),
  [Qlik](https://qlik.com/us/dashboard-examples/dashboard-design)). → the Executive Overview's
  KPI row answers the five "5-second" questions before any chart.
* **Not everything has equal weight** — design the flow of attention
  ([insightsoftware](https://insightsoftware.com/blog/best-practices-for-designing-and-building-a-great-kpi-dashboard/)).
  → one primary chart per section, secondary panels smaller.
* **Dark themes are low-light, not black;** separate surfaces clearly; few accents; boost text
  contrast ([Toptal](https://www.toptal.com/designers/ui/dark-ui-design),
  [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/dark-mode.md)).
  → navy-tinted surfaces, elevation via lighter surface + 1 px border, one cyan accent.
* **Chart colours need their own dark-mode check** — luminance contrast and adjacent-colour
  separation ([Chameleon, arXiv 2512.00516](https://arxiv.org/html/2512.00516)), and **colour is
  never the only cue** ([American Express](https://designinternet-qaeusw1green.americanexpress.com/guidelines/data-visualization/color)).
  → validated palette (§3); status always icon + label.
* **Control towers are exception-resolution tools,** ranked by business impact, with suggested
  actions kept distinct from approved ones
  ([Logistics Viewpoints](https://logisticsviewpoints.com/2026/09/24/the-control-tower-is-evolving-from-visibility-layer-to-decision-system/),
  [SCMR](https://www.scmr.com/article/the-exception-queue-is-where-supply-chain-ai-earns-its-roi/procurement)).
  → Risk & Exceptions is a ranked queue with owner, window and evidence; recommendations are
  labelled "suggested".

## 5. Shell mechanics

* **Global filters** (`src/filters/`): five multi-select dimensions; the **URL query string is
  the single source of truth** (shareable links, back button, survives reload and view
  switches). Options cascade faceted-search style: each dimension shows only values valid under
  the *other* filters, with live series counts; selections that stop matching are pruned, the
  dimension just edited is kept. Pure functions in `model.ts`, tested in isolation.
* **API layer** (`src/api/`): one typed function per endpoint; `ApiError` distinguishes
  *unreachable* (null status), *not generated* (503) and other failures; `useApi` aborts stale
  requests and offers retry. **No placeholder data path exists** — a view renders loading, the
  real response, or an explicit error.
* **States** (`src/components/ui.tsx`): skeleton, spinner, empty, error (unreachable / not
  generated / failed, with the failing route and Retry).
* **Route placeholders** show each view's questions, coverage and a **live** data-readiness
  table from `GET /datasets` — never invented values.
* **Dev wiring:** Vite proxies `/api/*` to FastAPI (`CELERIS_API`, default
  `http://127.0.0.1:8000`), so no CORS and relative URLs in production builds.

Chart library recommendation for Phase 2: **Apache ECharts** (canvas, handles 60k-row
series and dataZoom, crosshair tooltips, accessible aria labels, theme object fed from
`theme/chart.ts`) — or **Recharts** if bundle size matters more than interaction depth. One
library, chosen before any view is built.

## 7. Known limits / blockers

* The generic `GET /datasets/{name}?col=value` filter is single-valued; multi-select filters
  need small aggregation endpoints in Phase 2 (`toApiQuery` already forwards single values).
* `history` and `forecast_detail` are large CSVs (gitignored, regenerated by the pipeline);
  views must request aggregated or filtered slices, never the full files.
* Inter / JetBrains Mono load from Google Fonts; offline the system font stack is used.

## 9. Phase 3 — Executive Overview (delivered, `/overview`)

The first screen answers five questions before any scrolling:

| Question | Answer on screen | Source |
|---|---|---|
| How much demand do we expect? | KPI: 19-month forecast units (+ next 12 m vs last 12 m) | `/views/timeline` summary |
| How much revenue will it generate? | KPI: next-12-month revenue at the announced list prices, with change | `/views/timeline` summary |
| Is demand increasing or decreasing? | KPI deltas (arrow + sign) and the history → forecast timeline | `/views/timeline` |
| What could go wrong? | KPI: P10–P90 range of the 19-month total (band method shown); macro scenario impact (exact re-forecasts) | `/views/timeline`, `/scenario/presets` |
| What should I do now? | KPI: critical actions; Act-now list ranked by impact × severity × urgency × confidence, evidence on expand | `/intelligence/recommendations?priority=CRITICAL&<filters>` |

Below: revenue timeline, mix by region / family / channel (the problem statement's required
mix), and the evidence-based planning briefing (company-wide, labelled when filters are on).

* **Recommendations follow the global filters** (`api/app.py`): each card's scope is read from its
  evidence; a card is `direct` when its scope lies inside the selection, `context` when it is
  broader (e.g. the company-wide EV shift), and dropped when it lies outside - judged against the
  values the selection implies (a SKU implies its family, regions, channels and customers).
* **One request per dataset per page:** identical GETs are shared and cached for 60 s in the client,
  so the KPI row and both timelines make a single `/views/timeline` call (tested).
* Company-wide panels (scenario impact, briefing) say so instead of pretending to be filtered.

## 10. Phase 4 — Demand Explorer (delivered, `/explorer`)

Covers the required **demand explorer** (drill-down family → SKU → region → customer;
seasonality, zero months, lifecycle) and **history vs forecast on one timeline**, plus the optional
**lifecycle intelligence** view.

| Panel | What it shows | Endpoint |
|---|---|---|
| Drill path | breadcrumbs from the global filters; clicking a row pins that level, a crumb clears everything deeper - shareable and shared with every other view | (filters) |
| History and forecast | recovered demand → forecast with P10–P90; units / revenue; **"+ Shipped" overlay** shows where stockouts held shipments below true demand | `/views/timeline` |
| Seasonality | % above / below an average month (history bars from a true zero line, forecast line) or a year-over-year overlay | `/views/seasonality` |
| Order pattern | share of observed months with no order (a missing month is not a zero), series ordering in ≤ 70% of months, median cycle, Syntetos–Boylan demand classes | `/views/seasonality` |
| Lifecycle | status mix, series age, launch / EOL handovers in the forecast window (each launch paired with its predecessor's EOL) | `/views/lifecycle` |
| Drill table | members of the current level with 24 + 12-month sparkline, last / next 12 months, change, revenue, zero months, lifecycle or demand class | `/views/drilldown` |
| Series detail | once a SKU and region are pinned: product, lifecycle, order pattern, planning segment, the weighted parts of the risk score, reason codes and the recommendation | `/series/{sku}/{region}` |

New contract datasets `sku_lifecycle` and `series_profile` are exports of existing pipeline tables
(no new calculation).

## 11. Page aggregations and serving fixes

| Piece | Where | What it does |
|---|---|---|
| Server-side page views | `api/pages.py` | `GET /views/planning` (procurement KPIs, monthly plan, ABC-XYZ mix, next-cycle lines, capacity), `GET /views/anomalies` (counts by category / type, flagged months on the demand series, exact points for one SKU × region), `GET /views/data-health` (issue counts, cleaning rules, before / after profile of every raw file). Totals are computed over the FULL datasets with the global filters; tables get the top rows plus the true total. `tests/test_pages_api.py` checks the totals equal the frozen outputs. |
| No truncated sums | Risk, Planning, Anomaly Monitor, Data Health | pages never add up the first page of `/datasets/*` (default `limit`); small datasets are fetched whole, large ones aggregated on the server |
| Calendar bands | `CalendarForecast.tsx` | P10 / P90 from the calibrated monthly bands of `/views/timeline` (a sum of SKU bands overstates the range); the previous period uses recovered history where it falls in history |
| Landing page | `LandingPage.tsx` | every figure from the API (briefing, backtest metrics, manifest, timeline, registries); the hero chart is the real last 12 months + 19-month forecast; "—" while a request is pending, and one failed request never blanks the others |
| Status colour | `theme/chart.ts`, `tokens.css` | "good" is emerald `#34d399`, so a status is never confused with the lime forecast series / accent |
| Production serving | `api/app.py` | SPA routes registered last; API paths (exact first segment) return a JSON 404 instead of `index.html`; the `/api` prefix the build uses is stripped by the API |
